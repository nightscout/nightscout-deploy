## Held-target move: what was actually discriminated

The helper's checkpoint hook only coordinates the test; it supplies no Docker,
publisher, health or database result. After the real old container was confirmed
stopped, an owned PostgreSQL session held the exact synthetic tenant-A checkpoint
row `FOR UPDATE`. The target was observed blocked by that actual holder. Backend
assignment had advanced while the admitted route view remained old.

All four observations completed while the callback kept the actual publication
fence held:

* [A handshake was HTTP403 and its direct current-target handoff refused](captures/probe-cold.txt).
* [B's old-route-generation alarm was accepted](captures/probe-alarm-b.txt), and
  its actual subscriber received it without crossing into A.
* [A new maintenance publication pin refused](captures/probe-pin-busy.txt).
* B's canonical API3 write committed and its unchanged WebSocket received that
  unique timestamp, rather than matching a prior reading with the same value.

The row holder then committed and closed. Only actual eligible-target readiness
allowed route cutover. A reconnected/current data and [new-owner handoff](captures/probe-alarm-a.txt)
passed, with B's session unchanged. Durable consumer and projection digest stayed
identical; checkpoint position did not decrease. The [idle realtime worker still
held its actual owner resource and was included in real census](captures/probe-census.txt).
[Omitting it refused](captures/probe-omitted-idle.txt).

Backend/routes ended at generation8 and the private journal was complete. Earlier
failed observations were not reset: actual forward recovery completed at
[generation3](captures/recovery-first.txt) and [generation6](captures/recovery-second.txt).
[Generation4](captures/owner-separation-first-setup.txt) and
[generation7](captures/owner-separation-second-setup.txt) were explicitly labelled
setup moves to separate A/B owners again. Both tenants shared the stopped owner in
those setup moves and were affected; those calls are not B-unaffected evidence.
No boot incarnation was reused and no old map was restored.

Alarm assertions concern actual private transport/fanout/current authority and
placement routing. They do not claim clinical evaluator alarm creation, device
receipt or durable missed-alarm replay. Optional owner-settings routes are not
selected by this binding; no settings row was SQL-seeded to force an alarm.

## Reproduction and limits

Use the committed host instruments with explicit owned project/state/port and core
inputs, after the shipping preparation/bootstrap/provision/commission/prime steps.
`shipping-sharding.integration.test.js` and `shipping-replacement.integration.test.js`
are opt-in. The latter requires A on realtime-2 and B on realtime-1, with explicit
two logical shards; it refuses a different starting layout. The scripts in
[instruments](instruments/) record status, process custody and feed metadata only.

```bash
NS_UI_TEST_CORE=/absolute/owned/core \
NS_COMPOSE_SHARDING_STATE=/absolute/private/state \
NS_COMPOSE_SHARDING_PROJECT=ns-rt-binding-proof-20261112 \
NS_COMPOSE_SHARDING_PORT=18375 \
node --test --test-force-exit bindings/compose/multitenant/shipping-sharding.integration.test.js

NS_UI_TEST_CORE=/absolute/owned/core \
NS_COMPOSE_SHARDING_STATE=/absolute/private/state \
NS_COMPOSE_SHARDING_PROJECT=ns-rt-binding-proof-20261112 \
NS_COMPOSE_SHARDING_PORT=18375 NS_COMPOSE_REPLACEMENT_PROOF=1 \
node --test --test-force-exit bindings/compose/multitenant/shipping-replacement.integration.test.js
```

The final proof had both optional operator-script override inputs unset. Earlier
readonly overrides were diagnosis prototypes, followed by the fresh final image.
Node force-exit bounds stock XHR handles after awaited assertions and supported
client cleanup; no client dependency was patched. An early private XHR-abort
cleanup attempt was removed after it masked the test verdict.

The first three owned synthetic projects and their private state/volumes remain
retained and stopped. Automatic approval review rejected recursive overlay deletion;
the complete old overlay was preserved by same-filesystem rename instead, with no
file/journal deletion. No unsafe action was retried indirectly.

No full source suite, browser, enabled-corpus campaign, capacity measurement,
provider login or cloud deployment was run in this lane. Automatic failover and
missed-alarm replay remain outside the capability. The coordinator owns ordinary
history integration, SOURCE metadata for its selected joined source/cache candidate,
and one frozen comprehensive acceptance. Local custody/recovery details live in
